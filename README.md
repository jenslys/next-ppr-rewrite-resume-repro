# Next.js PPR resume + host rewrite reproduction

Related issue: [vercel/next.js#99500](https://github.com/vercel/next.js/issues/99500).

On Next.js **16.4.3**, an internal PPR resume can fail with:

```text
Invariant: postponed state should not be provided when fallback params are provided. This is a bug in Next.js.
```

The host rewrite resolves the concrete tenant URL, but placeholder routing query values leave the final `domain` param as `[domain]`.

## Run

Requires Node.js 22+ and npm. No Vercel account, deployment, database, credentials, environment file, or external service is needed.

Verified with Node.js 24.13.0 and the pinned dependencies below.

```sh
git clone https://github.com/jenslys/next-ppr-rewrite-resume-repro.git
cd next-ppr-rewrite-resume-repro
npm ci
npm run repro
```

`repro` builds the app, starts a loopback-only NextServer on an available port, sends five resume requests, then closes the server. It uses the actual postponed state generated by the build. Dependencies are pinned in `package-lock.json`.

**Expected behavior:** all five cases return 200 and render the concrete tenant/path.

**Actual behavior:** three controls pass and two cases fail with the invariant. **Exit code 1 is expected while the bug exists.** Framework error stacks are printed before the summary:

```text
200 public root, no routing query
200 public root, concrete routing query
500 public root, placeholder routing query
500 public article, placeholder routing query
200 concrete internal URL, placeholder routing query
AggregateError: 2/5 resume cases failed
```

After the first build, `npm test` reruns only the requests.

## What the harness models

- `cacheComponents: true`, `partialPrefetching: false`, and `instant = false`.
- A dynamic root layout at `/sites/[domain]/[[...slug]]`.
- One build-time tenant (`built.example`); requests use another (`runtime.example`).
- Host-based rewrites from `/` and `/article` into the internal tenant route.
- A Suspense boundary around `connection()` to generate postponed state.
- NextServer with `minimalMode: true` and `customServer: false`, matching the relevant options in `@vercel/next`'s server launcher.

The failing root request is equivalent to:

```text
POST /?nxtPdomain=%5Bdomain%5D&nxtPslug=%5B%5B...slug%5D%5D
Host: runtime.example
Next-Resume: 1
X-Matched-Path: /sites/[domain]/[[...slug]]
X-Nextjs-Rewritten-Path: /sites/runtime.example

<postponed state read from the build's .meta file>
```

The harness deliberately supplies the placeholder values to isolate the recovery failure. It does **not** reproduce or explain which Vercel routing step introduces them in production. This is an internal resume-protocol test, not a claim that an ordinary browser GET alone reproduces the failure.

## Parameter-recovery finding

For the failing article case, the harness prints:

```json
{
  "params": { "domain": "[domain]" },
  "rewrittenPathname": "/sites/runtime.example/article"
}
```

In `packages/next/src/server/base-server.ts`, the fallback parameter lookup uses:

```js
utils.dynamicRouteMatcher?.(normalizedUrlPath)
```

That checks the original public URL (`/article`), which cannot match `/sites/[domain]/[[...slug]]`. The correct rewritten pathname is already available.

In a separate diagnostic experiment, changing that lookup to use `rewrittenParsedUrl.pathname` made both failures return 200, while controls remained successful. That experiment is **not included** here: this repository runs unmodified Next.js, and the proposed direction still needs upstream route-precedence/rewrite-chain coverage.

All data is synthetic. Generated `.next` files, including ephemeral preview signing material, are excluded from Git.
